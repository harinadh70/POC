7. THE SERIAL LOAD CHAIN — LoadNextPage / LoadFirstPage
################################################################################

--- Legacy VBScript (lines 414-445) -------------------------------------------
    Sub LoadNextPage()
      If StrComp(Left(mstrNodeKey,3),"SYS",0) = 0 Then
        Call ExecuteAction(mstrAction, mstrNodeKey, 0, "")
      Else
        Select Case UCase(Left(mstrNodeKey,7))
          Case "POL|POL"
            Call ExecuteAction("TREE", "POL|POL|" & mstrExpiredNumber & "|", -1, "")
          Case Else
            Call ExecuteAction(mstrAction, "POL|POL|" & mstrExpiredNumber & "|", 0, "")
        End Select
      End If
    End Sub

    Sub LoadFirstPage
      Call ExecuteAction(mstrAction, "POL|POL|" & mstrExpiredNumber & "|", 0, "")
    End Sub

--- Actual POC -----------------------------------------------------------------
    Files: src/utils/data-strategy.ts (dataStrategy replaces the chain)
         + src/routes/routes.tsx (parent → child route nesting)

    This is the CLEANEST WIN — same as our earlier analysis, and the actual POC
    confirms it.

    The serial chain (menu.onload → LoadNextPage → tree.onload → LoadFirstPage)
    existed because loading all frames at once caused timing problems in IE.
    Each frame's onload triggered the next.

    In React Router 7, this chain is IMPLICIT:
        1. Root route loader runs (clientRootLoader — auth check)
        2. Root middleware runs (clientRootMiddleware — auth guard)
        3. dataStrategy runs (cycling, frame routing)
        4. Frame loader runs (clientStaticLoader or clientDynamicLoader)
        5. Component renders with loader data

    The parent → child ordering is guaranteed by React Router. No manual
    chaining needed.

    The PREFETCH_ROUTE_FRAGMENTS in data-strategy.ts shows the actual POC's
    awareness of the menu/tree/modal resource routes:
        const PREFETCH_ROUTE_FRAGMENTS = ['menu', 'tree', 'modal'] as const;

    STATUS: ELIMINATED (framework handles it — confirmed in actual POC)
