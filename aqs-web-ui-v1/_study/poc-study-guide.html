Part A

Learn it — the ideas behind the POC

Seven short sections. After these you can follow any question on the call.

A1

The 90-second story

The AQS insurance application is old — its screens are written in Classic ASP + VBScript, a 20-year-old Microsoft technology. It works, but it's hard to change, hard to hire for, and can't deliver a modern experience. We are moving the screens to React (today's standard for web UIs) without touching the business logic underneath.

The core insight — say this and everyone gets it

The old app already works by having the server describe each page as data and send commands the screen obeys. We kept that exact idea. We built one React “engine” that turns server data into a live page and runs the server's commands — so we modernize once, and every screen benefits.

There are 156+ Lines of Business (Policy, Business Owner's, Commercial Auto…). We are doing LOB 1 (Policy) now. The whole POC is designed to prove one thing: adding the other 155 is configuration, not new code.

A2

What actually got built (and runs)

A working React application you can open in a browser. It has a mock backend built in, so it runs on a laptop with no servers — perfect for a demo. The verified flow: Login → Dashboard (156 LOBs) → Policy Information → change a field → the server-driven command loop fires.

It compiles & runs
Clean install, passes TypeScript typecheck, builds for production, verified live in a browser.
Real stack
The exact technologies the design document (v13) specifies — not a toy.
29 source files
Small, because the engine is reused. That smallness is the proof.
Demo-ready
Mock backend stands in for the real .NET APIs; swappable via one interface.
A3

React, only the 8 words you'll hear

You don't need to write React. You need to recognize these eight words and know where each lives in our POC.

Component
A reusable piece of screen written as a function.
Ours: FormRenderer, FieldRenderer, Dashboard.
JSX
HTML written inside code. It just looks like HTML.
Ours: the tags inside every .tsx file.
Props
Inputs passed into a component.
Ours: a field's label, value, required-flag.
State
Data that changes while you work; the screen redraws itself.
Ours: the current form values, which field is visible.
Hook
Reusable behaviour named use….
Ours: useAuthStore, usePageStore.
Store (Zustand)
The app's shared memory.
Ours: auth, app, page, browser-command stores.
Router
Maps a URL to a page, and fetches its data first.
Ours: router.tsx, one route serves every LOB.
Loader
Runs before a page shows to get its data.
Ours: lobPageLoader — the legacy Window_OnLoad.
A4

The architecture — the 156-LOB answer

The whole codebase splits into two zones that never mix. This split is the most important thing to understand and the strongest thing to say.

engine/ — write once, freeze
Everything generic: the renderers that draw fields, the command runner, the page loader, the API contract. It has zero knowledge of Policy or any LOB. If adding an LOB meant editing the engine, the design failed.
lobs/ — pure configuration
A registry of 156 entries + one folder per LOB with its page configs. LOB 1 (Policy) is filled in; the other 155 are placeholders that visibly slot in.
Say this

“Onboarding a new Line of Business is a config entry and a folder — we never touch the engine. That's how one team delivers 156 LOBs instead of building 156 apps.”

A5

How a page loads — the two-call flow

When a user opens a page, two backend calls happen, then the engine draws it. Walk through this left-to-right if anyone asks “how does it actually work?”

1 · Loader runs
Router runs the page's loader before showing anything
→
2 · Navigation API
Backend says which page/window to load
→
3 · PageBuild API
Backend runs the legacy DLL, converts XML→JSON: fields + actions + commands
→
4 · Render + obey
Engine draws the fields, then runs any startup commands

Then the user acts (types, clicks) → a third call, the Page Layout API, runs the legacy logic and returns the next commands. Every call is a thin wrapper around the unchanged legacy code.

A6

The server-driven command loop (the demo “aha”)

This is the single most impressive thing to demo, so understand it well. The backend can send about 20 commands the UI obeys — e.g. SET_VISIBLE, SET_REQUIRED, LOAD_COMBO, DISPLAY_WARNING, NAVIGATE.

In our POC: change Policy Status → Cancelled. The field change calls the backend; the backend replies with three commands — “make the Cancellation Reason field visible”, “make it required”, “warn the user”. The React screen instantly obeys: the field appears and a warning pops up. Nobody wrote page code for that — the engine simply ran the server's commands.

Say this while demoing

“I changed one field. The server decided what happens next and sent commands; the React engine obeyed. This is exactly how the legacy screen behaves — same brain, new face.”

Part B

The 15 sprint tasks — in detail, with what to say

Each card: What it is (plain) · How we solved it (the real approach in this POC) · Say it (your talk track) · If asked (a follow-up you can field). Status pills: BUILT substantially done · PARTIAL proven, finishing left.

01

Architecture Design

InitialBUILT

What it is

Decide the overall shape: how state, routing, rendering, the nav tree, and the dashboard fit together — and how it scales to 156 LOBs.

How we solved it

The two-zone design: a frozen engine/ + a config-only lobs/ registry. One shared contract of types (Controls, Commands, PageBuild) that every LOB speaks.

Say it

“The architecture is one reusable engine plus per-LOB configuration. That decision is what makes 156 LOBs feasible with one codebase.”

If asked “why not build each page normally?” — 156 LOBs × dozens of pages each = thousands of screens. Hand-building doesn't scale; a config-driven engine does.
02

Project Setup

SetupPARTIAL

What it is

The folders, files, and service layer — the skeleton every other task builds on.

How we solved it

A feature-sliced tree: engine/ · lobs/ · stores/ · pages/ · shell/ · mock/ · types/, wired with Vite + TypeScript. Clean install, builds green.

Say it

“The project is set up so responsibilities are obvious: generic engine, per-LOB config, shared state, and pages. New engineers know exactly where things go.”

If asked what's left — hardening the service layer and adding lint/test config; the structure itself is in place.
03

State Management

CoreBUILT

What it is

The app's shared memory — who's logged in, global variables, and the current page's live data.

How we solved it

Four Zustand stores (per SDD §3): authStore (session + permissions), appStore (global variables + dirty flag), browserCommandStore (messages, modals), pageStore (the current form's controls & values).

Say it

“State is split into focused stores. The page store is where server-driven UI happens — commands mutate it and the screen redraws.”

If asked why Zustand — it's the design doc's choice: tiny, simple, and readable outside components (so loaders can use it too).
04

APIs

CoreBUILT

What it is

The four backend touchpoints: Login, Navigation, PageBuild, Server Call.

How we solved it

One typed contract — AqsApi with navigate(), pageBuild(), pageLayout(). A mock implements it now; the real .NET wrappers implement the same interface later. No engine change to swap.

Say it

“We coded to an interface, not a specific server. The mock proves the flow today; pointing it at the real .NET APIs is a drop-in.”

If asked about the real backend — thin .NET 4.8 wrapper APIs that call the existing DLLs and return JSON; no business logic is rewritten.
05

TS Conversion — Load

CoreBUILT

What it is

Port the legacy Window_OnLoad — the code that runs when a page opens — to TypeScript.

How we solved it

React Router loaders. Our lobPageLoader runs before the page renders, doing the Navigation → PageBuild calls. That's the modern home for on-load logic.

Say it

“The legacy on-load became a route loader — data is fetched before the screen appears, so there's no flicker or half-drawn page.”

If asked about VBScript logic — decision logic (which window/frame) is ported to execute-action; data-fetch on load is the loader.
06

JSON Schema / Renderer

CoreBUILT

What it is

Decide the shape of the page-data (JSON) and write the code that turns it into a screen.

How we solved it

A typed PageBuildResponse (controls + actions + grids + commands) and the FieldRenderer/FormRenderer that draw it. Three render strategies — dynamic / static / hybrid — chosen per page.

Say it

“One renderer draws any field from its type. A page is described by JSON; the renderer never hard-codes a screen.”

If asked about layouts that need a custom look — that's the hybrid strategy: a static schema for layout merged with live server values.
07

Event Handling

CoreBUILT

What it is

Handle user events (onClick, onChange/onBlur) and do the right thing — often calling the server.

How we solved it

A single choke-point, executeAction, plus a command dispatch that runs the ~20 server command verbs. Fields fire it on change/blur; buttons fire it on click. This is the loop we demo.

Say it

“Every user action funnels through one function, so behaviour is consistent everywhere. The server responds with commands; we execute them. You'll see it live.”

If asked for the command list — SET_VISIBLE/DISABLED/REQUIRED/TEXT, LOAD_COMBO, NAVIGATE, DISPLAY_WARNING/ERROR/MESSAGE, OPEN_WINDOW, and more.
08

Page Renderer

CoreBUILT

What it is

Render an entire page dynamically from its data.

How we solved it

One generic host, LobPage, for every LOB and page. It loads the data and hands controls to the renderer, grids to the DataGrid, buttons to the buttons renderer.

Say it

“There's a single page component that renders every page in the whole system. The differences come from data and config, not new components.”

If asked “literally one page component?” — yes; that's the scale story made concrete.
09

Modal Renderer

CorePARTIAL

What it is

Load and manage pop-up dialogs (e.g. Add Named Insured).

How we solved it

The frame switch in execute-action recognizes MODAL and stages a modal command in the browser-command store; a modal host consumes it. Notifications (DISPLAY_*) already render.

Say it

“Modals reuse the same engine — a modal is just a page rendered in a dialog frame. The routing to a modal is wired; the dialog host is the finishing step.”

If asked what's left — mounting the modal page inside a draggable MUI Dialog; the command and state plumbing exist.
10

Routing

CoreBUILT

What it is

The basic router — URL to page.

How we solved it

React Router data-router. The key route is /lob/:lob/:pageId — one route with one loader serves every LOB and every page.

Say it

“One parameterized route handles all 156 LOBs. Add an LOB and its pages just work — routing needs no changes.”

If asked about old ASP URLs — a route mapper converts legacy .asp names to React routes, so existing links keep working.
11

Login

ImplementationBUILT

What it is

Sign in and store the session + permissions.

How we solved it

A Login page that seeds the authStore (userId, CompLoc, LOB, permissions). Protected routes redirect to login when not signed in.

Say it

“Login establishes the session that every backend call carries. The POC accepts any credentials; production calls the real Auth API.”

If asked about security — the design doc covers auth, API security, and threat protection; the POC focuses on the UI engine.
12

Dashboard

ImplementationPARTIAL

What it is

The landing page with entry points (“new policy” buttons).

How we solved it

The Dashboard renders the 156-LOB registry as tiles — 1 active (Policy), 155 config-ready — plus a quick-start into Policy Information. It is the scale visual.

Say it

“The dashboard shows the whole story at a glance: 156 LOBs, one active, one shared engine. Clicking Policy takes you straight into the working flow.”

If asked what's left — real per-user LOB permissions and live “new business” actions; the layout and scale view are done.
13

Policy Start

ImplementationPARTIAL

What it is

Begin the Policy (LOB 1) flow and render its first screen.

How we solved it

Clicking Policy routes into /lob/POL/policy-information; the loader fetches the page and the engine renders it. The Policy LOB config declares its pages.

Say it

“Starting a policy is just entering the Policy LOB's first configured page — the engine takes it from there.”

If asked about multiple policy pages — each is another entry in the Policy config; the same loader + renderer serve them all.
14

Policy Information — 1

ImplementationBUILT

What it is

Create the page's JSON config and a page-specific component.

How we solved it

policy-config.ts declares the page: title, version, hybrid strategy, tabs, grid list, permissions. The PageBuild supplies the live controls. This is the “create JSON” deliverable.

Say it

“Policy Information is described by a versioned config plus live server data. Its page-specific needs live in config — not in bespoke code.”

If asked why “hybrid” — the page has a fixed layout/permissions (static schema) merged with live values from the server.
15

Policy Information — 2

ImplementationPARTIAL

What it is

Render the full page (grids excluded for this pass).

How we solved it

The engine renders all field types (text, select, date, combo, number, textarea), tabs, action buttons, and the live command loop. A Coverage DataGrid is included as a bonus.

Say it

“The full Policy Information page renders end-to-end, including the server-driven behaviour. Grids were scoped out for this pass, but our grid engine already handles them.”

If asked to prove grids work — the Coverage tab shows a live DataGrid from the same config-driven approach.

Part D

Q&A bank — answers ready to go

Tap to expand. Read them once; they'll be there if you need them.

Why React, and why this approach?

React builds pages from data with reusable parts. Because the legacy app is already server-driven, we keep that contract and only replace the browser layer — so one engine covers every screen instead of rewriting hundreds by hand.

Are we rewriting the business logic or the backend?

No. The design principle is “no API-first redesign.” New APIs are thin wrappers around the existing DLLs. Business rules and databases are untouched — that's what keeps risk low and rollout phased.

How does adding LOB 2 actually work?

Add a config folder for the LOB and one line in the registry. Routing, rendering, events, modals, grids, and state are all provided by the shared engine. No engine changes.

What's genuinely done vs. remaining?

Done: the whole engine (state, APIs, loaders, renderer, events) and the Login→Dashboard→Policy flow with the live command loop. Remaining for polish: the modal dialog host, per-user permissions on the dashboard, and grid coverage on Policy Information (scoped out this pass).

Is this the real code or a mock?

The engine and UI are real, best-practice React on the design-doc stack. The backend is mocked so it runs standalone for the demo; swapping in the real .NET APIs is a single interface implementation, no engine change.

How long to migrate a page once the engine exists?

For a dynamic page, mostly config. The design doc's step-by-step: analyze the legacy ASP/VBS/XML once, then the page renders from PageBuild. Complexity affects effort, not the process.

What are the risks?

Field types not yet covered by the renderer, grid edge-cases, and unusual commands. All are additive — they extend the engine, they don't change its shape. Multi-window and modal polish are known follow-ups in the design doc.

Why is the codebase so small?

Because the engine is reused. Small is the proof: if every page needed its own code, 156 LOBs would be enormous. It isn't.

Part F

Glossary

Every term you'll hear, in one line.

LOB
Line of Business — a product area (Policy, Commercial Auto…). There are 156+.
ASP / VBScript
The legacy technology the current screens are built in.
Engine
Our reusable, LOB-agnostic code that renders any page and runs commands.
Registry
The list of 156 LOBs; adding one is a new entry here.
Navigation API
First backend call — which page/window loads next.
PageBuild API
Second call — the page as JSON (fields, actions, commands).
Page Layout API
Called on a user action — runs legacy logic, returns commands.
Wrapper API
A thin .NET endpoint that calls the existing DLL and returns JSON.
BrowserCommand
An instruction from the server (SET_VISIBLE, DISPLAY_WARNING…) the UI obeys.
matchcode
The short code that identifies a field/button (e.g. POLSTAT).
PageBuild / Data Island
The page data; legacy embedded it as XML, now converted to JSON.
Render strategy
dynamic (server only) / static / hybrid (config schema + server values).
Loader
Runs before a page renders to fetch its data (the old Window_OnLoad).
Store
Shared state container (auth, app, page, browser-command).
CompLoc
Company/location code on every request (defaults to PIHW).
Frame
Where an action's result goes: MAIN, MODAL, NEWWINDOW, HIDDEN.
