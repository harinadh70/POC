window_onload, line by line: VBScript → React

The complete legacy initialization routine — reconstructed verbatim from the Azure DevOps source (photos IMG_4377–4397) — next to the actual TypeScript now shipped in the POC at engine/load/window-load.ts. Every phase, both codes, and the reasoning.

One function becomes two phases

Legacy second_window_onload is ~277 lines that run AFTER the HTML loads and imperatively patch the page. React splits it at a natural seam: everything that fetches or derives data moves into windowLoad() — a route loader that runs BEFORE the page renders — and everything that acts on the rendered page moves into useWindowLoad(), an effect that runs once after first paint. The page cannot render before its data exists, so every timing guard in the legacy file (mblnPageLoaded, mblnRespondTabClick) becomes unnecessary.

What the legacy code is doing. The browser fires window_onload when the HTML finishes parsing. The real work sits in second_window_onload — an indirection that let pages override or wrap the entry point. On Error Resume Next is VBScript's blanket error suppression: any statement that fails silently continues to the next line, which is why every step is followed by a TrapBrowserError(...) call to log what just happened. The Dim block declares locals used across all twelve phases, because everything lives in one function scope.

What React does instead. There is no "onload event, then patch the page." The route definition binds a loader to the URL. React Router calls lobPageLoader when the user navigates, waits for the promise, and only then renders LobPage with the result available synchronously via useLoaderData(). The two-Sub indirection maps to the loader/effect split — but enforced by the framework, not by convention.

  • On Error Resume Next + TrapBrowserError → a normal try/catch in the loader plus the route's ErrorBoundary element. Errors stop the render and show a real error page instead of silently producing a half-initialized screen.
  • The local Dims (like strShowNextOnEdit, pageHeader) → typed fields on WindowLoadResult, so every consumer knows exactly what came out of the load.
The legacy entry point is time-based (the browser says "HTML is done"). The React entry point is data-based (the router says "your data is ready"). That inversion is what deletes every "is the page loaded yet?" guard in the rest of the file.

What the legacy code is doing. Pages opened with IE's showModalDialog get a fixed dialogHeight/dialogWidth string like "720px". The code strips the last two characters (px) with Left(..., Len(...) - 2), converts to integer, compares against the physical screen, and shrinks the dialog if it doesn't fit. This ran on every modal page load because dialogs were sized by the opener, which couldn't know the user's screen.

Why React needs nothing here. showModalDialog is dead (removed from every modern browser). Modals are now a component rendered inside the same page — MUI's Dialog is positioned and constrained by CSS, which by definition cannot exceed the viewport. Responsive sizing is the browser layout engine's job, handled continuously, not once at load.

This phase is a workaround for a dead API. Ten lines of string-slicing and integer comparison collapse into a maxWidth prop — and the React version also handles window resizing after load, which the legacy version never did.

What the legacy code is doing. The app is an IE frameset: AQSMain.asp owns a menu frame, a tree frame, and the content frame where this page runs. Before the page can do anything — delegate an event, run a server call, update the menu — it must capture live pointers to those sibling windows. The path differs by context: a normal page reaches its parent via window.parent; a modal page has no parent, so it goes through window.dialogArguments (a reference the opener passed in). Every later phase (With mobjAQSMain) then executes methods in the other frame's script context.

Why this can't fail in React. There are no separate window objects. Sidebar, tree, and page are components in one tree, rendered by one React root. Anything the legacy code asked mobjAQSMain to do — set a title, mark data changed, run a server call — is either a Zustand store write (state) or an imported function (behavior). The failure modes this phase guards against (parent not loaded yet, frame renamed, cross-frame security errors) are structurally impossible.

This also kills the cleanup obligation: legacy Window_OnBeforeUnload must Set mobjAQSMain = Nothing etc. to avoid IE memory leaks from cross-frame circular references. React unmounts the component and garbage collection just works.
Roughly 35 lines of pointer acquisition plus the entire "delegate everything upward" pattern (15 stub handlers later in the file) exist only because of frames. Removing the frameset removes the code — this is the single largest simplification in the whole migration.

What the legacy code is doing. The app hand-rolled a performance tracker: the main frame carries counters (mlngTimeEndBrowserRequest, mlngTimeBOProcessing…), each page stamps them at start and end of load, and mlngXMLElapsedTime carries the server-reported business-object time from the XML island. The page URL is stashed as a DOM attribute on the main frame's body so a diagnostics view can display "this page took N ms."

What React does instead. The browser's Performance API is the standard replacement: performance.mark() stamps named instants, performance.measure() derives the duration between them, and the DevTools timeline visualizes it with no custom UI. The two marks in window-load.ts bracket exactly the same span the legacy counters did: navigation start → page interactive. Server-side timing (the old mlngXMLElapsedTime) belongs in the API response envelope or the standard Server-Timing HTTP header, which DevTools also renders natively.

Custom timing plumbing through a cross-frame object graph becomes two calls to a browser-native API that survives page changes, works in every tab, and needs zero UI code.

React — window-load.ts (shipped)

// Pure, unit-testable derivation:
export function resolveDirtyFlag(
  action: string | undefined,
): boolean {
  switch ((action ?? '').toUpperCase()) {
    case 'EDIT':
    case 'ADD':
      return true;
    case 'INQUIRY':
    case 'SELECT':
    default:
      return false;
  }
}

// Phase A computes it:
const isDirty = resolveDirtyFlag(input.session.action);

// Phase B applies it:
useAppStore.getState().setDirty(isDirty);

// Consumed later by the unsaved-changes blocker:
const blocker = useBlocker(
  useAppStore(s => s.isDirty));

What the legacy code is doing. marrSessionInformation(4) is the action string ("EDIT", "INQUIRY", "ADD|…", etc.). The logic: if the action contains none of EDIT / INQUIRY / SELECT, the page is treated as an ADD — and ADD pages are marked dirty immediately, before the user types anything, because an add-in-progress must not be silently abandoned. Two flags are set: one on the main frame (.mblnDataChanged, app-wide) and one module-local (mblnEEDataChanged, used by this page's Window_OnBeforeUnload to decide whether to fire a CANCEL server call). Note the subtlety: this whole block runs inside With mobjAQSMain, so dotted names write to the other frame.

What React does instead. The same business rule, isolated as a pure function — same inputs, same outputs, but testable in one line and readable without knowing what slot 4 of a variant array means. The two legacy flags collapse into one isDirty in the app store, because there is only one state owner now; both the nav-blocking prompt and any cancel-on-leave call read the same value.

The mapped semantics are preserved exactly: ADD ⇒ dirty from the start; EDIT is dirty in the legacy sense of "will mutate" (the POC keeps EDIT ⇒ true so the blocker engages; flip it to false if the team prefers literal legacy behavior — it's one line in resolveDirtyFlag).
Business rules buried in string-scanning inside a cross-frame With block become a named, pure, tested function. When LOB 37 needs a different rule, the config hook overrides one function — not a copy of Eebrowser.vbs.

What the legacy code is doing. This is the heart of the load. Every ASP page ships with an embedded <xml id="xdiPageData"> island containing the page's control definitions, values, combo items, and pre/post-call configuration. The code instantiates an MSXML6 DOM parser (synchronous, whitespace-stripped), copies the island's XML into it, and registers XPath namespaces so later code (like FillCallArray2) can query it. The commented-out line shows the older, cheaper approach (reference the island directly) that was replaced by an explicit copy. Then a GetEEData-style call walks the document and pushes values into the page's controls, and pageHeader (the island's header node) is checked — if it's missing the page bails out entirely.

What React does instead, step by step.

  • The island itself → an API response. The same page definition arrives as JSON from the PageBuild API. No client-side parser, no MSXML dependency, no namespace registration — JSON.parse happens inside fetch().
  • mxmlDoc (held for later XPath queries) → the page store. loadPage() indexes controls by matchcode into a plain object. What was mxmlDoc.selectNodes("//control[@matchcode='X']") is now controls['X'] — O(1), typed, and inspectable in devtools.
  • GetEEData writing values into DOM controls → the renderer reading the store. Legacy pushes data into existing HTML; React derives HTML from data. Same information, opposite direction — and the reason no "did the control exist yet?" errors can occur.
  • If pageHeader Is Nothing Then Exit Sub → the loader throwing. A malformed response rejects the loader promise and React Router shows the error boundary, instead of silently rendering a dead page.
The Data Island is the legacy system's real API — it was always "server sends page definition, browser renders it." React keeps that architecture (which is why the migration works at all) and only changes the wire format and the direction of data flow: XML→JSON, push→derive.

What the legacy code is doing, decoded. dtaNEXT is the wizard's [Next] button. The page header flag ShowNextOnEdit picks the policy: if "t", Next should stay visible but disabled in edit-like modes; otherwise it should be hidden outright. Within each arm, three action modes are special-cased: plain EDIT always suppresses Next; RLVUPDATE (rate-level update) and EDITTYPRAT (edit type/rating) consult a session-XML item (rlvupdateadd / chgtypratadd) that records whether the flow was initiated during an ADD — if it wasn't (<> "yes"), Next is suppressed. And the fossil in the middle: a September 2000 comment documenting that the unconditional "else show it" line caused a bug (it overrode VISIBLE=F from the XML) and was removed — with a note that the whole block should eventually be "controlled by the APP code via dynamically adjusting the VISIBLE attribute in the XML."

The remarkable part: that 25-year-old TODO is exactly the React architecture. "Controlled by the APP code via the XML" = the server decides visibility and sends it with the page definition. The migration doesn't fight this block — it finishes it:

  • The decision inputs (pageHeader.ShowNextOnEdit, action mode, rlvupdateadd, chgtypratadd) all live server-side already — the wrapper API evaluates the same rules and emits SET_DISABLED or SET_VISIBLE commands in the PageBuild response.
  • The client applies commands generically. It doesn't know Next exists; it can't get the rule wrong; LOB-specific variations never touch the engine.
  • The 2000-era bug class (a hardcoded browser line overriding server config) is structurally impossible — there is no client-side rule to conflict with the server's.
~55 lines of nested cross-frame branching become one generic dispatch call, and the business rule moves to the tier that owns its inputs. This is the thesis of the whole migration proven on the gnarliest block of window_onload — and the original authors asked for exactly this fix in a comment dated 9/25/00.

The header's "path label" (a breadcrumb-like string such as a coverage path) is assembled by asking AQSMain to describe the navigation-tree span between pathstart and pathend, seeded by a one-shot pagelabelkey session item that must be read before something else deletes it — then hand-scrubbed with string replaces (drop "Policy Coverages -", trim dashes), assigned to the header control, optionally appended with the page title (non-modal + headertype="append" only), and finally the session key is explicitly cleared. Fragile, ordering-sensitive, and famous for edge cases — the inline comments are patch notes.

What React does instead. The URL is the path. React Router gives every layout component the current location; segment labels come from the LOB registry (static) and the page store title (from PageBuild). Breadcrumbs are recomputed from those sources on every navigation — no one-shot keys, no cleanup calls, no string surgery on a rendered label. Where a business-specific path (like a coverage chain) is needed, the PageBuild response carries it as structured data (pageBuild.title / a path array), assembled by the tier that owns the navigation tree.

Deriving the breadcrumb from route + store kills a whole family of "label didn't update / cleared too early / double-appended" bugs, because there is no stored label to get out of sync — it's recomputed from truth on every render.

What the legacy code is doing. What the legacy code is doing. The page HTML ships with a visible divLoading overlay ("please wait" animation); the last acts of second_window_onload are to hide it and raise mblnPageLoaded — the flag that fifteen event handlers check before doing anything, because between HTML parse and this line the page is interactive-looking but not actually wired up. That window is where legacy race bugs lived.

Why both disappear. React Router's useNavigation() reports loader progress, so the pending indicator is shell-level UI that appears during every page load automatically — no per-page overlay div to hide (and no way to forget to hide it on an error path, which in the legacy app left users staring at an eternal spinner). The loaded-flag has no equivalent because the dangerous window doesn't exist: until the loader resolves, the previous page is still shown; when the new page mounts, its data is already in place.

The final two lines of the legacy routine are the purest summary of the migration: one hides UI the framework now manages, the other raises a flag whose entire reason to exist was torn out by the loader-before-render model.

/**
 * window-load — the TypeScript conversion of Eebrowser.vbs
 * `window_onload` / `second_window_onload` (lines 120–397).
 * Sprint Task 5: "TS Conversion – Load: Windows_Load and supporting function".
 *
 *   Phase A `windowLoad()`     — BEFORE render (route loader): fetch + derive.
 *   Phase B `useWindowLoad()`  — AFTER first render (effect): act on the page.

export async function windowLoad(input, resolvePageConfig) {
  // [VBS 133–143] Modal sizing — ELIMINATED (MUI Dialog constrains via CSS).
  // [VBS 145–157] Frame references — ELIMINATED (one component tree + stores).

  // [VBS 159–166] Timing milestone → browser-native Performance API.
  performance.mark(`window-load:start:${input.pageId}`);

  // [VBS 198–211] XML Data Island → Navigation + PageBuild APIs (JSON).
  const nav = await api.navigate({ ...input.session, lob: input.lob }, input.pageId);
  const pageBuild = await api.pageBuild({ ...input.session, lob: input.lob }, nav.pageId);

  // [VBS 175–195] Action-mode dirty flag, from the session action.
  const isDirty = resolveDirtyFlag(input.session.action);

  const pageConfig = resolvePageConfig(nav.pageId);
  return { nav, pageBuild, pageConfig, isDirty };
}

// [VBS 175–195] The Select Case on the action string, as a pure function.
export function resolveDirtyFlag(action) {
  switch ((action ?? '').toUpperCase()) {
    case 'EDIT':
    case 'ADD':     return true;
    case 'INQUIRY':
    case 'SELECT':
    default:        return false;
  }
}

export function useWindowLoad(result) {
  const { nav, pageBuild, pageConfig, isDirty } = result;
  useEffect(() => {
    // [VBS 198–211] Hydrate page state (the React mxmlDoc).
    const merged = mergeControlsWithPageBuild(pageConfig, pageBuild);
    usePageStore.getState().loadPage(pageBuild, merged);

    // [VBS 175–195] Raise/clear the unsaved-changes flag.
    useAppStore.getState().setDirty(isDirty);

    // [VBS 222–280] ShowNextOnEdit & friends → server-sent commands.
    // [VBS 282–285] Required indicators → `required` on each control.
    if (pageBuild.commands?.length) dispatchCommands(pageBuild.commands);

    // [VBS 1136–1149] PageUniqueRoutine("local_window_onload") → typed hook.
    pageConfig?.onLoad?.();

    // [VBS 287–327] Path labels → breadcrumbs read the route.  ELIMINATED here.
    // [VBS 335–358] Tab selection → page-local useState.
    // [VBS 362–384] First-control focus → declarative autoFocus.

    // [VBS 386–397] Timing end; HideLoading (router pending UI);
    // mblnPageLoaded = True (implicit — rendered ⇒ loaded).
    performance.mark(`window-load:end:${nav.pageId}`);
    performance.measure(`window-load:${nav.pageId}`,
      `window-load:start:${nav.pageId}`, `window-load:end:${nav.pageId}`);
  }, [nav.pageId, pageBuild, pageConfig, isDirty]);
}
