Before vs After · "Windows on Click" · explained for confident talking

The same feature — clumsy port vs. done right.

Some clicks in AQS open a separate window. The recovered code opens it the exact way the 20-year-old VBScript did — which causes real problems in a modern browser. Here's each problem, the fix, why it's better, and the one line to say so you can hold your own with any engineer.

The 20-second primer (so the rest lands)

A "window" = a separate browser pop-up window. "On click" = it happens when the user clicks something. The rule to remember: the old code was copied line-for-line from VBScript, so it kept habits that were fine in 2005 but are wrong for a browser today. Every fix below is about doing the same feature the modern, safe way.

00 — CONTEXT

What actually happens on a click

The click asks the server "what next?" The server says frame: NEWWINDOW — "open this in a separate window." The code then builds a web address, opens a pop-up, and shows it. Simple in theory. The five problems below are all in how it does that.

01 — REUSE THE WINDOW

Every click opens a brand-new window

The biggest issue — and it's a real bug against your own design doc (SDD §11: "one window per policy").

▲ Now — the problem
// a NEW unique name every single time
const windowName =
  `AQS_Window_${policyId}_${timestamp}`;
window.open(url, windowName, features);
Because the name has a timestamp, it's different on every click. The browser can only reuse a window if the name matches — so it never reuses. Click 5 times → 5 windows pile up.
● Better — the fix
// stable key → reuse the same window
const existing = registry.get(key);
if (existing && !existing.closed) {
  existing.focus();   // bring it forward
  return 'focused';
}
// else open one and remember it
registry.set(key, window.open(url, `AQS_${key}`, features));
A registry (a little address book of open windows) keyed by policy+page. If one's already open, focus it. One window per policy — exactly what the design doc asks for.
🧠 Analogy: The old way is like opening a new browser tab every time you click a link to the same page — you end up with 20 tabs of the same thing. The fix switches you to the tab you already have open.
💬 Say this

"The current port names every popup uniquely with a timestamp, so `window.open`'s name-reuse never fires — every click spawns a new window. I'd add a window registry keyed by policy so we reuse and focus, which is what SDD §11 specifies anyway."

02 — KEEP DATA OUT OF THE ADDRESS BAR

Sensitive data is passed in the web address

The pop-up's URL carries the raw session detail — visible, logged, and stored in history.

▲ Now — the problem
// packs everything into the URL
params.set('action', followupAction);
params.set('nodeKey', nodeKey);
params.set('policyId', policyId);
params.set('xmlDetail', xmlDetail); // ← big & sensitive
url = `/form/${file}/${policyId}?${params}`;
All of it — including xmlDetail (a chunk of policy data) — sits in the address bar. That's saved in browser history, server logs, and anything watching the URL.
● Better — the fix
// hand off privately, keep URL clean
if (req.state)
  setHandoff('aqs:handoff:' + key, req.state);
// URL now carries only a tiny route
window.open(req.url, `AQS_${key}`, features);
The data goes into sessionStorage — a private, in-browser drawer the new window reads on startup. The URL stays short and safe. This is the SDD §11.7 approach.
🧠 Analogy: The old way writes the customer's details on a postcard — anyone handling it can read them. The fix puts them in a sealed envelope handed directly to the recipient.
💬 Say this

"We're putting `xmlDetail` and session values in the popup's query string — that leaks into history and logs. The design doc says the child window should read its state from sessionStorage, so I'd hand off there and keep the URL minimal."

03 — CALM MESSAGES, NOT BROWSER ALERTS

A blocked pop-up throws a jarring browser alert

It uses the raw alert() box instead of the app's own notification system.

▲ Now — the problem
if (!newWindow || newWindow.closed) {
  alert(
    'Pop-up blocked!\n\n' +
    'Please allow pop-ups for this site...'
  );
}
alert() freezes the whole page, looks like a system error, can't be styled, and ignores the app's design. Every other message in the app uses a clean banner — this one doesn't.
● Better — the fix
if (!handle || handle.closed) {
  notify('warning',
    'Pop-up blocked. Please allow pop-ups...');
  return 'blocked';
}
Routes through the app's notification system — the same in-app banner used everywhere else. Non-blocking, on-brand, accessible. Matches SDD §11.10.
🧠 Analogy: The old way is a blaring fire alarm that stops everything. The fix is a polite notification that slides in and lets you keep working.
💬 Say this

"Popup-blocked uses a native `alert()`, which blocks the UI and breaks our design language. I'd route it through our notification store like every other message — the SDD even calls for an in-app banner."

04 — ONE SAFETY GUARD, NOT THREE

The loop-prevention logic is scattered and duplicated

The "don't open windows forever" safety check lives in three places across two files.

▲ Now — the problem
// guard A — in execute-action.ts
if (popupContext || sessionGuardMatched) …
// guard B — in the provider
if (window.opener && url === current) return;
// guard C — also in the provider
if (lastOpenedUrlRef.current === url) return;
Three overlapping checks in two files. They can drift apart, and the reconstruction even flagged "duplicate command logic exists twice." Hard to reason about, easy to break.
● Better — the fix
// one guard, one place
if (deps.isChildWindow()) return 'skipped';
// reuse handles the "already open" case,
// so the other two guards disappear
The registry (fix #1) already prevents duplicates, so two of the three guards vanish. One clear rule — "never open from inside a popup" — in one module.
🧠 Analogy: The old way has three different people all checking the same door lock and sometimes disagreeing. The fix is one doorman who owns the door.
💬 Say this

"Loop-prevention is duplicated across execute-action and the provider — three guards that can drift. Once we have the registry, dedup is automatic, so I'd consolidate to a single guard in one window-manager module."

05 — TESTABLE, AND NO DATA IN THE LOGS

Can't be tested, and it prints session data to the console

It calls the browser directly (untestable) and logs customer/session details.

▲ Now — the problem
console.log('[DEBUG] 📘 NEW WINDOW OPENING');
console.log('[DEBUG] sessionInformation:',
            sessionInfo); // ← prints PII
// calls window.open directly → hard to test
Leftover [DEBUG] lines print session info, policy id, node key to the browser console — noise and a small data leak. And because it talks to the browser directly, it can't be unit-tested.
● Better — the fix
// browser access is injected → testable
createWindowManager({
  openWindow, isChildWindow,
  setHandoff, notify,
});
// debug logs removed; use logger.debug if needed
The browser calls are passed in, so a test can swap in fakes and verify behavior. Debug logs are gone. Cleaner, safer, verifiable.
🧠 Analogy: The old way is a car welded shut — you can't service it — that also prints the customer's details on every receipt. The fix opens the hood for servicing and stops printing private data.
💬 Say this

"There are leftover debug logs printing session data, and the code calls `window.open` directly so it isn't testable. I'd inject the browser dependencies behind a small interface and drop the console logs — testable and no PII in the console."

★ — THE ONE THING TO SAY

If you remember one sentence

The confident summary

"The window-on-click code is a literal 1-to-1 port of the old VBScript — it works, but it keeps browser-unfriendly habits: it spawns a new window every click, passes sensitive data in the URL, uses a jarring native alert, and duplicates its safety checks. The fix is the window registry from our own design doc §11 — reuse and focus one window per policy, hand off state via sessionStorage, use our in-app notifications, and consolidate the guards. One clean module replaces all of it."

That single paragraph names the problem, the cause, the fix, and cites the design doc — which is exactly how a senior engineer would frame it.

📖 — GLOSSARY

Every term you just used, in one line

window.open()
The browser command that opens a new pop-up window.
Registry
A small in-memory address book of the windows we've opened, so we can reuse them.
focus()
Bring an already-open window to the front instead of opening another.
sessionStorage
A private in-browser drawer for data — not shown in the address bar.
Query string / URL params
The ?key=value part of a web address; visible and logged.
PII
Personally identifiable / sensitive data (e.g. policy details) that shouldn't leak.
alert()
The old, page-freezing browser message box.
Guard
A safety check that stops something bad (here: opening windows in an endless loop).
window.opener
A flag that's set only when the current window was opened by another — i.e. "am I a pop-up?"
Inject / injectable
Passing a component's dependencies in from outside, so you can swap them in tests.
Unit test
An automated check that a small piece of code behaves correctly.
SDD §11
The Multi-Window Support section of your Solution Design Document — the "target" design these fixes align to.
