Codebase Guide · every file explained

What each file does, and how they connect.

All 29 source files of aqs-web-ui-poc, in the order data flows through them. Each entry: its role, what's inside, and what it connects to. The colored chip tells you which architecture zone it lives in — that's the whole mental model.

BUILD ENGINE · frozen CONFIG · per-LOB STATE PAGE SHELL

How the app wakes up (the 60-second mental model)

  1. index.html loads main.tsx, which mounts App.tsx.
  2. App.tsx sets the theme, mounts the router, and the notification host.
  3. The router shows Login; signing in fills the auth store.
  4. Dashboard reads the LOB registry and draws 156 tiles.
  5. Clicking Policy hits the /lob/:lob/:pageId route; its loader calls the API (Navigation → PageBuild).
  6. The page store gets the controls; FormRenderer + FieldRenderer draw them.
  7. A field change calls executeAction → API → dispatch runs the returned commands → the store updates → the screen redraws.
01

Build & entry BUILD

The plumbing that turns source files into a running app. You'll rarely open these, but here's what they do.

package.jsonBUILD33 lines
The project's manifest — dependencies and commands.
Lists every library the app needs (React, MUI, Zustand, React Router, Vite, Tailwind) and the scripts: dev (run locally), build (production), typecheck.
Connects: npm install reads it to fetch libraries into node_modules.
vite.config.tsBUILD18 lines
Configures the Vite dev server & build.
Turns on the React and Tailwind plugins and sets the @/ path alias (so imports read @/engine/... instead of long relative paths). Sets the dev port to 5173.
Connects: used by every npm run dev / build.
tsconfig.jsonBUILD25 lines
TypeScript's rulebook.
Turns on strict type-checking (catches mistakes before runtime) and declares the same @/ alias so the type-checker resolves imports.
Connects: drives npm run typecheck and editor type hints.
index.htmlBUILD12 lines
The single HTML page the whole app lives in.
Contains one empty <div id="root"> and loads main.tsx. React fills that div — this is what "Single Page Application" means.
Connects: loads src/main.tsx.
src/main.tsxBUILD10 lines
The ignition — hands control to React.
Finds the #root div and renders <App/> into it. Also imports the global CSS.
Connects: renders App.tsx; imports index.css.
src/index.cssBUILD16 lines
Global styles & the Tailwind import.
Pulls in Tailwind's utilities and sets base font/height. Component styling is mostly done through the MUI theme, so this file stays tiny.
Connects: imported by main.tsx; pairs with theme.ts.
src/vite-env.d.tsBUILD1 line
Type hints for Vite features.
A one-line reference so TypeScript understands Vite-specific things (like importing images or env vars).
Connects: ambient — used by the type-checker only.
Also present: README.md (how to run + architecture), .gitignore, .claude/launch.json (dev-server config), and generated package-lock.json / dist/. None are app logic.
02

The shared contract ENGINE

One file that defines the "language" every other file speaks. Read this and you understand the data model.

src/types/index.tsENGINE196 lines
Every shape of data in the app, in one place.
Defines the vocabulary: SessionInfo (who/where you are), LobDefinition (one Line of Business), ControlDef (a single field), PageBuildResponse (a whole page as data), BrowserCommand (the ~20 server commands like SET_VISIBLE), ExecuteActionResult, and PageConfig (a page's static/hybrid config). Crucially, nothing here is Policy-specific — an LOB is data, never a new type.
Connects: imported by almost every file — it's the contract the engine and the config both obey.
03

Look & feel

src/theme/theme.tsSHELL31 lines
The design tokens — colors, spacing, typography.
Creates the MUI theme: the blue primary color, the neutral background, rounded corners, default input sizes. Change a value here and the whole app restyles consistently (SDD §7.4).
Connects: consumed by App.tsx's ThemeProvider; every MUI component reads it.
04

The backend boundary ENGINE

The only place the app talks to a server. Swapping the mock for the real .NET APIs happens here — and nowhere else.

src/engine/api/client.tsENGINE33 lines
The backend contract (an interface) + the active implementation.
Declares AqsApi with three methods: navigate() (which page loads), pageBuild() (the page as JSON), pageLayout() (run a user action). Exports api — currently the mock. The engine only ever knows this interface.
Connects: the loader and execute-action call api; the real backend would replace the one export.
src/mock/mock-backend.tsMOCK146 lines
A fake .NET backend so the POC runs with no server.
Implements the three API methods with sample Policy data: the Policy Information fields, a Coverage grid, action buttons. It also contains the demo rule — when Policy Status becomes "Cancelled", it returns SET_VISIBLE + SET_REQUIRED + DISPLAY_WARNING commands. This is the only file that changes when you plug in the real backend.
Connects: imported by client.ts; produces the JSON the renderers draw.
05

State — the four stores STATE

The app's shared memory, split into four focused stores (SDD §3). "Store" = a small box of data any component can read, that redraws the screen when it changes.

src/stores/auth-store.tsSTATE24 lines
Who is logged in.
Holds the session (userId, CompLoc, LOB) and permissions, with login(), logout(), and can(permission).
Connects: set by Login; read by the layout, the loader, and executeAction (to send the session).
src/stores/app-store.tsSTATE27 lines
Global variables & the "unsaved changes" flag.
The React home for the legacy session array and dirty flag — variables addressed by name (set via SET_VARIABLE commands).
Connects: written by command handling; read wherever page-global values matter.
src/stores/browser-command-store.tsSTATE36 lines
Messages & modal requests from the server.
Holds the notification queue (from DISPLAY_* commands) and a pending-modal slot. Provides notify(), openModal().
Connects: written by dispatch; read by NotificationHost.
src/stores/page-store.tsSTATE81 lines
The live state of the currently-open page — where server-driven UI happens.
Holds the page's controls (keyed by matchcode) and their values. Key method: applyCommands() — takes server commands (SET_VISIBLE, SET_REQUIRED, LOAD_COMBO…) and mutates the controls, which makes the screen redraw. loadPage() seeds it; setValue() updates one field.
Connects: loaded by LobPage; mutated by dispatch; read by FormRenderer/FieldRenderer.
06

The engine — command core ENGINE

The two files that make it "server-driven". This is the heart of the migration.

src/engine/commands/execute-action.tsENGINE58 lines
The single choke-point for "the user did something".
Gathers the current form values, calls the Page Layout API, then acts on the result's frame (the ported VBScript switch): MODAL opens a dialog, MAIN navigates, HIDDEN just applies commands. It hands the returned commands to dispatch.
Connects: called by FieldRenderer & ButtonsRenderer; calls api and dispatch.
src/engine/commands/dispatch.tsENGINE64 lines
The command runner — the React version of legacy command-handlers.
Takes the list of server commands and routes each one: control commands (SET_VISIBLE etc.) go to the page store; message commands (DISPLAY_WARNING etc.) go to the browser-command store; navigation commands are returned to the caller. Every server command verb is handled here.
Connects: called by execute-action and LobPage; writes to the page & browser-command stores.
07

The engine — renderers ENGINE

The components that turn page-data into a visible screen. None of them know anything about Policy.

src/engine/renderers/FieldRenderer.tsxENGINE190 lines
Draws ONE field from its type — the legacy .htc → MUI mapping made real.
A switch on the field type: text→TextField, select→dropdown, combo→Autocomplete, date→date input, checkbox/radio/number/textarea. It reads/writes the page store, and fires executeAction on change (dropdowns) or blur (text) — that's what triggers the server loop.
Connects: used by FormRenderer; reads page store; calls executeAction. The biggest engine file, and the most reused.
src/engine/renderers/FormRenderer.tsxENGINE36 lines
Lays out all the page's fields in a grid.
Reads the control list from the page store and renders each via FieldRenderer in a responsive 2-column layout. Zero knowledge of any specific page.
Connects: rendered by LobPage; reads page store; uses FieldRenderer.
src/engine/renderers/DataGridRenderer.tsxENGINE36 lines
Turns any server list into a sortable grid (legacy XmlList → MUI DataGrid).
Takes a list's columns + rows and renders a compact, paginated MUI DataGrid. Any page's lists render through this — no per-list component.
Connects: rendered by LobPage for each grid in the PageBuild.
src/engine/renderers/ButtonsRenderer.tsxENGINE47 lines
Renders the page's action buttons and wires their clicks.
Draws each action button, styling it by its action (Save→filled, Cancel→plain), and routes clicks through executeAction.
Connects: rendered by LobPage; calls executeAction.
08

The engine — notifications ENGINE

src/engine/modal/NotificationHost.tsxENGINE25 lines
Shows the server's messages (the warning you see in the demo).
Watches the browser-command store and renders each DISPLAY_* message as an MUI Alert/snackbar. Mounted once at the app root so any page's messages appear.
Connects: mounted by App.tsx; reads the browser-command store (fed by dispatch).
09

The LOB config zone CONFIG

The other half of the architecture: pure configuration. This is where an LOB is data. The engine above never imports these specifics.

src/lobs/registry.tsCONFIG55 lines
THE registry — the thesis of the whole POC.
Builds the list of 156 Lines of Business: LOB 1 (Policy) is fully defined; the six other real ones (BOP/CAU/IRM/WRM/LIA/RMP) are named; the rest are generated placeholders. Helpers: getLob(), lobStats(). Adding an LOB = one entry here.
Connects: read by the Dashboard (tiles) and the loader (to find a page's config).
src/lobs/policy/policy-config.tsCONFIG41 lines
LOB 1 — Policy. The one fully-wired line of business.
Declares the Policy LOB and its Policy Information page: title, version, hybrid strategy, tabs, grid list, permissions. Also its dashboard entry points. Everything Policy-specific is here as data — nothing in the engine.
Connects: imported by registry.ts; used by Dashboard and the loader's merge step.
src/lobs/_template/README.mdCONFIG50 lines
The copy-me guide for LOB 2 … 156.
A short recipe: make a config folder, export a LobDefinition, add one line to the registry, point the backend at its pages. States explicitly: no engine changes.
Connects: documentation — the proof that onboarding is config-only.
10

Routing glue PAGE

src/config/routes.tsENGINE28 lines
Two small helpers used everywhere.
pageIdToPath() maps a backend pageId to a URL (generic across LOBs). mergeControlsWithPageBuild() implements the static/hybrid merge (SDD §10.2.2): for hybrid pages, the static schema is the base and live server values are merged in; for dynamic pages, server data passes through.
Connects: used by FieldRenderer/ButtonsRenderer (navigation) and LobPage (merge).
src/router.tsxPAGE30 lines
The route table.
Defines: /login, the protected layout, /dashboard, and the star route /lob/:lob/:pageId with its loader — one route serves every LOB and every page. Errors fall back to the error boundary.
Connects: mounted by App.tsx; wires pages + the loader.
11

Pages PAGE

The three screens. Notice there's only one for all LOB pages.

src/pages/Login.tsxPAGE48 lines
Sign-in (sprint task 11).
A simple form that, on submit, fills the auth store with the session + permissions and navigates to the dashboard. The POC accepts any credentials.
Connects: writes auth-store; navigates via the router.
src/pages/Dashboard.tsxPAGE108 lines
The landing page — and the scale story made visual (task 12).
Shows the stat row (156 LOBs · 1 active · 155 config-ready · 1 engine) and renders the registry as tiles: Policy is clickable, the rest are dimmed "config-ready". A quick-start button jumps into Policy Information.
Connects: reads registry.ts & policy-config; navigates to the LOB route.
src/pages/LobPage.tsxPAGE99 lines
The ONE generic page host for every LOB page (task 8).
Two parts: (1) the exported loader — runs before render, doing Navigation → PageBuild (this is the ported Window_OnLoad); (2) the component — loads the data into the page store, applies startup commands, and renders the title, tabs, FormRenderer, grids, and action buttons. It resolves nothing LOB-specific itself.
Connects: wired in router.tsx; uses the API, page store, dispatch, and all renderers. The keystone file.

Shell & root SHELL

src/shell/AppLayout.tsxSHELL52 lines
The frame around every signed-in page (SDD §2.2).
The top AppBar with brand, the current user, and Logout — with the routed page shown below it. Also guards auth: not signed in → redirect to Login.
Connects: the parent route in router.tsx; reads auth-store.
src/shell/ErrorBoundary.tsxSHELL28 lines
The "something went wrong" fallback (SDD §2.7).
If a page or its loader throws, this shows a contained error card with a way back to the dashboard — instead of blanking the whole app.
Connects: set as the errorElement in the router.
src/App.tsxSHELL20 lines
The root component — assembles the app.
Wraps everything in the theme, mounts the router, and mounts the NotificationHost. Small, because it just wires the big pieces together.
Connects: rendered by main.tsx; pulls in theme, router, NotificationHost.
★

The one-sentence summary

Everything in engine/, stores/, types/ is written once and frozen. Everything in lobs/ is configuration. A new Line of Business touches only the config side — which is exactly why 156 LOBs is one small codebase, not 156.
