POC Briefing · Legacy ASP → React

Everything you need to speak to this POC — even if you don't write React.

This is the migration of the legacy ASP / VBScript insurance screens (TMNAS · AQS Portal) to a modern React + MUI front end, backed by thin .NET 4.8 wrapper APIs over the existing DLLs. One reusable engine renders every page from server data — you don't rebuild each screen by hand. Below is the whole story plus a fast React primer, framed around the 15 sprint tasks and aligned to Solution Design Doc v13.

01 — THE ONE IDEA

Hold onto this one sentence

The whole architecture in a line

The server sends the page as data (fields, buttons, grids) plus a list of commands; React's job is to render that data and obey those commands. We built the renderer + the command-runner once, and it works for every screen.

The legacy app already thinks in terms of a server that streams back XML describing what to show and what to do. We did not throw that away — we kept the exact same backend contract and replaced only the browser side. That is why this is a POC that scales: prove the engine on Policy Information, and every other page is mostly configuration afterward.

What to say on the call

“Instead of hand-coding 200 screens, we built a single engine that turns the server's page-data into a live React page and executes the server's commands. Adding a new page becomes config, not new code.”

The four design principles (straight from the v13 design doc)

Backend-first ownership

All business rules, validations and processing stay in the backend. The UI never owns logic.

UI as a render layer

The React app only presents, captures interaction, and calls the backend. Nothing more.

No API-first redesign

There are no new business APIs — thin .NET 4.8 wrapper APIs call the existing legacy DLLs in-process.

Incremental modernization

New React UI coexists with the legacy AQS app during transition — phased rollout, low risk.

02 — REACT IN TEN MINUTES

The only React words you'll hear

Eight ideas. Each one: plain-English meaning, then where it lives in this app so you can point at it.

Component

A reusable piece of screen — a button, a form, a whole page. Written as a function that returns what to show.
Here: form-renderer.tsx, data-grid.tsx, PolicyInformation.tsx.

JSX

HTML written inside the code so a component can describe its own markup. It just looks like HTML.
Here: the <Field/>, <DataGrid/> tags you'll see inside every .tsx file.

Props

The inputs you pass into a component — like function arguments. “Render this field, disabled.”
Here: a field's matchcode, label, value, required-flag are all props.

State

Data that can change while the user works; when it changes, the screen re-draws itself automatically.
Here: the current form values, which modal is open, the user's permissions.

Hook

A reusable bundle of behaviour, named use…. Drop it into a component to gain that behaviour.
Here: use-form-commit, use-modal-state, use-smart-navigation.

Context / Provider

Shared data made available to the whole app without passing it down by hand — the app's “global memory”.
Here: global-variable-provider, form-provider, browser-commands-provider. This is “State Management”, task 3.

Router

Maps a URL to the page component to show. Also runs a “loader” to fetch that page's data first.
Here: routes.tsx + frame-router. Task 10.

Loader

A function the router runs before a page shows, to go get its data from the server.
Here: every features/*/utils/loader.ts. This is where legacy Window_OnLoad moved to. Task 5.

That's genuinely enough to follow any part of this codebase. Everything else is these eight ideas combined.

03 — HOW A PAGE LOADS

One page, start to finish

The exact round-trip. When someone asks “how does it actually work?”, walk them left-to-right through this.

1 · URL
User navigates to a route, e.g. /policy/information
→
2 · Loader
Router runs the route's loader (dataStrategy) before rendering
→
3 · Navigation API
Backend validates session, returns which page/window to load next
→
4 · PageBuild API
Backend calls legacy DLL, converts XML→JSON: controls + actions + BrowserCommands
5 · Normalize
normalize-service-config + data-grid-normalize shape it for the UI
→
6 · Render
FormRenderer / FieldRenderer / DataGrid draw the page (MUI)
→
7 · User acts
Click / change → handler calls Page Layout API via executeAction
→
8 · Commands
Backend returns commands → command-handlers apply them → back to step 6

Two backend calls open a page — Navigation API (what to load) then PageBuild API (how to draw it). Steps 6 → 7 → 8 are the live loop; every backend call is a wrapper that runs the unchanged legacy DLL and returns JSON.

04 — THE MIGRATION ENGINE

How legacy ASP / VBScript became React

These four pieces are the actual “conversion”. Each maps a legacy concept to a React one — and each is real, reconstructed code.

Route mapping — asp-route-mapper.ts

Turns a legacy page name like PolicyInformation.asp into a React route and back again (aspToReactRoute() / reactToAspRoute()). Old links keep working; nothing has to be rewritten by hand.

Window logic — execute-action.ts

The legacy VBScript decided, on every action, whether to open a modal, a new window, or replace the page. That exact switch (the code even cites Main_ISLLSYS_20010101.vbs line 1633) is now a clean TypeScript function branching on the frame type:

  • MODAL — open a dialog on top of the page
  • NEWWINDOW — open a separate window
  • HIDDEN — run work with no visible page change
  • MAIN — replace the current page

Server commands — command-handlers.ts

The largest, most-photographed file (105 shots). The server can tell the UI to do ~20 specific things, and this file executes each one. This is why the UI stays “driven by the backend” just like the legacy app:

Everything visual is one of three reusable systems — build once, reuse everywhere: the form/field renderer (draws any field from its matchcode), the modal-dialog engine (use-modal-state / -data / -actions), and the data-grid (any server list becomes a sortable table via a small config entry).

06 — THE DEMO

The flow to show: Login → Dashboard → Policy Information

This is the plan's payoff (tasks 11–15). Narrate what happens underneath at each step — it proves the engine.

  1. Login — user signs in; the session (user, permissions, CompLoc) is stored in the app's shared state. features/auth + permission-store.
  2. Dashboard — lands on the home screen; “new policy” buttons are rendered from server data, not hardcoded. pages/dashboard.tsx.
  3. Open Policy Information — the route's loader fires an xmlServerCall, gets the PageBuild JSON, and the form-renderer draws every field from its matchcode. PolicyInformation.tsx.
  4. Interact — change a field → executeAction → server returns commands (e.g. SET_VISIBLE, LOAD_COMBO) → command-handlers apply them live. This is the “aha” moment — the same server-driven behaviour as the legacy screen, now in React.

Honest scope note for the room: grids on Policy Information are explicitly excluded in task 15 for this pass, and modals are proven separately — keep the demo on the field-render + command loop, which is the core proof.

07 — QUESTIONS YOU'LL GET

Answers ready to go

Why React, and why is this the right approach?

React lets us build the page from data with reusable components. Because the legacy app is already server-driven (the server describes each page), we keep that contract and only replace the browser layer — so one engine covers every screen instead of rewriting hundreds by hand.

What's the technology stack?

Frontend: React + Vite + TypeScript, with React Router (loaders) for navigation, Zustand for state (three stores), and MUI v7 + Tailwind v4 for the UI with design tokens. Backend: new .NET Framework 4.8 “wrapper” APIs on IIS that call the existing legacy DLLs and return JSON. The business logic and databases are untouched.

Are we rewriting the backend or the business logic?

No. That's the whole point of the design — “no API-first redesign.” The new APIs are thin wrappers around the existing DLLs, invoked in-process. We modernize the UI without touching proven business rules, which is what keeps the risk low and the rollout phased.

How is state / data managed?

Through React “providers” — shared memory for the whole app: global variables, the current form's values, the user's permissions, and browser commands. When data changes, the affected parts of the screen redraw automatically. That's task 3, and it's built.

How does a legacy .asp page end up as a React page?

Four steps: the route mapper converts the old page name to a React route; the loader calls the same backend and gets the page as JSON; the renderer draws the fields/buttons/grids; and the command-handler runs whatever the server tells it to. No screen is hand-rebuilt.

What about all the VBScript logic — is it lost?

No — the decision logic (which window to open, what to do on an action) was ported into execute-action.ts, which even references the original VBS line numbers. The server-side business rules are unchanged; we reuse them.

What's actually done vs. remaining?

The Core engine (state, APIs, loaders, renderer, events, modals — tasks 3–9) is built and recovered. Remaining for the one-day push: finish routing wiring (10), dashboard buttons (12), and the Policy Information render (13–15). Grids are deliberately out of scope for this pass.

How long to add a brand-new page later?

Mostly configuration: one grid-config entry per list, one thin feature hook, and a route. The renderer, modal engine, and command-runner are already shared, so new pages don't need new engine code.

What are the risks?

Main ones: fields whose matchcodes aren't yet covered by the renderer, grid rendering (explicitly deferred), and edge-case commands. All are additive — they extend the engine, they don't change its shape.

08 — GLOSSARY

Terms you'll hear, in one line each

ASP / VBScript
The legacy technology the current screens are written in — server-rendered pages with VBScript logic.
Navigation API
First backend call on any page — validates the session and returns which page/window to load next.
PageBuild API
Second call — returns the page as JSON (fields, actions, browser-commands), converted from the legacy XML.
Page Layout API
Called when the user acts (click/change) — runs the legacy logic and returns the next set of commands.
Wrapper API
A thin .NET 4.8 endpoint that adds no business logic — it just calls the existing legacy DLL and returns JSON.
Data Island
The XML block the legacy ASP page embedded its data in — now converted to JSON in the backend instead.
matchcode
The short code identifying a field or button (e.g. BLDCLS, ADD). The renderer draws a control from its matchcode.
NodeKey / LOB
Where you are in the navigation tree; LOB = Line of Business (POL, BOP, CAU…) — the product area.
CompLoc
Company/location code carried on every request (defaults to PIHW server-side).
SessionInfo
The bundle of who/where you are (user, policy, node, action) sent with requests.
Frame
Where an action's result goes: MODAL, NEWWINDOW, HIDDEN, or MAIN.
Loader
The function that fetches a page's data before it renders — where legacy Window_OnLoad now lives.
Provider
A React shared-state container the whole app can read — the app's global memory.
