1 — SCOPE

Purpose & scope

This LLD specifies the front-end engine of the AQS migration POC to implementation depth. It is the missing companion to the SDD v13 (a high-level/solution document) and the referenced-but-unshared API Design Document. Backend internals (the .NET wrapper APIs and legacy DLLs) are treated as an external contract (§4) — this document does not design them.

Design rules the whole system obeys

  • Engine ↔ config separation. Engine code is LOB-agnostic and never imports LOB specifics. An LOB is data (config), never new engine types.
  • Server-driven UI. The backend returns page-data + commands; the client renders data and executes commands. No business logic on the client.
  • Code to interfaces. The engine depends on the AqsApi interface, not a concrete backend.
  • Single source of truth types. All shapes live in one module (types/index.ts) and are shared by engine and config.

4 — API CONTRACTS

The backend contract (AqsApi)

Three methods. The engine depends only on this interface; the mock and the real .NET wrappers both implement it.

interface AqsApi {
  navigate(session: SessionInfo, target: string): Promise<NavigationResponse>
  pageBuild(session: SessionInfo, pageId: string): Promise<PageBuildResponse>
  pageLayout(session: SessionInfo, req: {
    matchcode: string; action?: string; value?: unknown;
    formData: Record<string, unknown>
  }): Promise<ExecuteActionResult>
}
MethodWhenRequestResponse
navigatePage open (step 1)session, target pageIdNavigationResponse — which page/window + frame
pageBuildPage open (step 2)session, resolved pageIdPageBuildResponse — controls, actions, grids, initial commands
pageLayoutUser actionsession, {matchcode, action?, value?, formData}ExecuteActionResult — outcome, frame, commands, navigateTo?
Real backend mapping: each method is a .NET 4.8 wrapper endpoint that invokes the legacy DLL in-process and converts its XML to these JSON shapes. Swap the implementation by exporting a different api from client.ts; no engine change.

pageStore.applyCommands — the server-driven core

Iterates commands; for each control-targeting verb it produces a new control object with the mutated flag/value, replacing it in controls. Because the store is reactive, every subscribed FieldRenderer re-renders. Non-control verbs are ignored here (handled by the dispatcher against other stores/router).

10 — RENDER STRATEGY

Strategies & the merge algorithm

StrategySource of truthmergeControlsWithPageBuild

mergeControlsWithPageBuild(cfg, pb):
  if !cfg || cfg.strategy==='dynamic' || !cfg.controls: return pb.controls
  liveByCode = map(pb.controls by matchcode)
  return cfg.controls.map(sc =>
    live = liveByCode[sc.matchcode]
    live ? { ...sc, value: live.value, options: live.options ?? sc.options } : sc)
11 — EXTENSION

Adding a Line of Business (config schema)

  1. Create src/lobs/<lob>/<lob>-config.ts exporting a LobDefinition (code, name, navPrefix, status:'active', pages).
  2. For each page, add a PageConfig (pageId, title, version, strategy, tabs?, controls? for static/hybrid, gridListNames?, permissions?).
  3. Register it: import into registry.ts and add to LOB_REGISTRY.
  4. Backend: ensure the wrapper APIs return PageBuild for the new pageIds. Dynamic pages need nothing more.
Invariant: no engine file is edited. Routing, rendering, events, grids, modals, and state are already provided. This is the property the POC exists to prove.
