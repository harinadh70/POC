What changed and why

  • mblnPageLoaded → eliminated entirely. In VBScript, every handler checks this flag because the page HTML loads before window_onload finishes, so users can click things before the page is ready. In React, the route loader fetches data BEFORE the component renders — the page literally cannot appear until it's ready. No flag needed.
  • mblnCallServer / mblnDoBrowserCommands → eliminated. These prevent re-entrant server calls (a server call during a server call). React's async/await pattern handles this naturally — executeAction returns a Promise, so callers can await it. For the recursive CALL_SERVER scenario, the POC uses a depth guard (maxDepth: 3) in the existing use-form-commit hook.
  • mblnEEDataChanged → appStore.isDirty. Same purpose (track unsaved changes), but it's a reactive Zustand property — any component can read it with useAppStore(s => s.isDirty) and will re-render when it changes. No manual checking.
  • mblnNavButtonClicked → not needed. This flag distinguishes "user clicked a navigation button" from "user closed the browser tab." In React, useBlocker from React Router handles in-app navigation blocking, and the beforeunload event handles browser close. They're separate code paths, not flag-checked in one handler.
  • mobjAQSMain / mobjMenuFrame / mobjTreeFrame → eliminated. There are no frames. The entire app is one React component tree. The sidebar, header, and content area are all children of AppLayout, sharing state through Zustand stores. No cross-frame references, no Set obj = Nothing cleanup.
  • mxmlDoc (XML Data Island) → pageStore.controls. The XML Data Island was an XML document embedded in the page HTML that contained the page's control definitions, matchcodes, and server call configurations. In React, the PageBuild API returns this as JSON. The pageStore.loadPage() method normalizes it into a Record<string, ControlDef> map.
  • marrEEData(12) → ActionRequest typed object. The 13-slot array with indices 0–12 (where slot 1 = matchcode, slot 5 = pre/post indicator, slot 8 = rule attribute, slot 12 = control XML) becomes { matchcode, action, value, formData }. Named properties instead of numeric indices.
  • marrSessionInformation() → authStore.session. A typed SessionInfo object with named properties (userId, compLoc, policyId, etc.) instead of a positional array.
  • marrServerCalls() → server-side. The pre/post-process call chain configuration moves to the backend. The client doesn't need to know which server routines will run — it just sends the action and the server handles the chain.
  • mobjServerRequest (XMLHTTP object) → fetch(). The browser's native fetch API replaces the ActiveX MSXML2.XMLHTTP.6.0 object. No CreateObject, no Set obj = Nothing cleanup.

What changed and why

VBScript requires explicit initialization because Dim gives you an uninitialized Variant. Boolean flags default to False but it's defensive practice to set them. Object refs must be Set ... = Nothing to avoid stale pointer errors.

React/JS doesn't need a separate init block because Zustand's create() function takes the initial state as its argument — the declaration IS the initialization. And JavaScript uses garbage collection, so there's no Set obj = Nothing pattern. When a component unmounts, its refs are cleaned up automatically.

The 5 Set ... = Nothing lines at the bottom of the VBS init block are entirely unnecessary in JavaScript — objects are garbage-collected when no references remain. The React equivalent is simply not holding the reference in the first place.

Why the delegation pattern exists (and why it disappears)

The architectural reason: In the legacy frameset, business logic (what happens when a user focuses/clicks/changes a control) lives in AQSMain.asp — the parent frame. The content page (where EEBrowser runs) only has the HTML controls and this thin delegation layer. Every user interaction must cross the frame boundary to reach the logic. The mblnPageLoaded check prevents events during initialization. The Is Nothing check prevents errors if the frame reference failed.

In React: There is no frame boundary. The component that renders the control also contains the event handler. The handler calls executeAction() directly (which calls the backend API). The two-check pattern (mblnPageLoaded + Is Nothing) disappears because: (1) the component can't receive events before it renders, and (2) there are no frame references to be null.

The GetRef* functions (lines 435–446): These exist because VBScript doesn't support first-class functions. GetRef("OnFocusHandler") returns a function pointer that can be assigned to an element's event handler via Set element.onfocus = GetRefOnFocusHandler(). In JavaScript, functions ARE first-class values — you pass them directly: onFocus={handleFocus}. The entire GetRef pattern is a VBScript limitation workaround.

Detailed explanation

What FillCallArray2 does: Given a matchcode (e.g., "PolicyStatus") and a type ("pre" or "post"), it runs an XPath query against the XML Data Island to find all configured server calls. It builds a 2D array (marrServerCalls) where each row has 4 columns: subroutine name, object name, parameter, and call type. This array is later used by CallServer to tell the backend which subroutines to execute.

The circular data flow problem: The server creates the XML Data Island (containing the call config), sends it to the browser, the browser parses it with FillCallArray2, then the browser sends that same configuration back to the server in CallServer. The data round-trips through the browser unnecessarily.

The React solution: The server keeps the call chain configuration. When the client sends an action (via api.pageLayout()), the server looks up the pre/post calls in the same configuration source it used to build the original Data Island. The client just says "PolicyStatus changed to Cancelled" — the server handles the rest. This eliminates:

  • The mxmlDoc.selectNodes() XPath query
  • The marrServerCalls 2D array and its ReDim
  • The for-loop that reads XML attributes into array slots
  • The entire concept of the client parsing server-side call configuration

Detailed breakdown

  • PageUniqueRoutine (1136–1149): VBScript's Execute is equivalent to JavaScript's eval() — it runs a string as code. EEBrowser uses it to call page-specific functions that may or may not exist on the current page. For example, a policy page might have a Sub local_window_onload() in its own script block. Execute "local_window_onload" calls it; if it doesn't exist, On Error Resume Next swallows the error.

    In React, this customization pattern becomes typed config objects. Each LOB has a config file (lobs/policy/policy-config.ts) with optional hooks. The engine calls them with optional chaining: pageConfig?.onLoad?.(). This is fundamentally safer because:
    • TypeScript catches hook name typos at build time
    • No runtime eval() — no code injection risk
    • Each hook's signature is typed — the engine guarantees what arguments it provides
    • Missing hooks are undefined, not runtime errors
  • SelectControlText (1152–1204, 52 lines): A two-level Select Case switch that handles every possible control type in the legacy system. It first checks the ID prefix ("inf"/"cal" → redirect to the date control "dta" prefix), then switches on the tag name (OBJECT → check ActiveX CLSID, RADIOBUTTON, IBUTTON, XMLLIST, COMBO, KPCOMBO, SELECT, INPUT → sub-switch on type, TEXTAREA). For the ActiveX OBJECT cases, it checks literal CLSIDs (COM class identifiers) for Protoview date/time and numeric controls.

    In React: onFocus={(e) => e.target.select()}. One line. The 52-line switch exists because the legacy system has 10+ different control types (native HTML, ActiveX, custom HTC behaviors) that all handle focus differently. MUI normalizes all of this — a TextField, DatePicker, Autocomplete, etc. all support the standard onFocus event. The ID prefix convention ("inf"/"cal"/"dta") disappears because each field component contains its own info button and calendar icon as MUI InputAdornment — no external button with a name-linked ID.
  • ReDimBrowserArray (1210–1219): ReDim is VBScript's array resize operation. VBScript arrays have a fixed size set at creation; to grow them, you must ReDim Preserve (allocate new, copy old, replace reference). This function centralizes that for two module-level arrays. JavaScript arrays are dynamic — .push(), .splice(), spread ([...arr, newItem]) all work without resizing. This function solves a language limitation that doesn't exist in JavaScript.
  • ShowUserMessage (1221–1231): Creates a UserMessage ActiveX object (a custom COM component) to display a modal dialog with a message, type (Error/Warning/Info), and button options (OK, OK/Cancel, etc.). It blocks execution until the user responds and returns the button they clicked. In React, browserCommandStore.notify(severity, message) adds a notification to the store, and the NotificationHost component renders it as a non-blocking MUI Snackbar with auto-dismiss. For blocking confirmations (like "are you sure you want to delete?"), MUI's <Dialog> with action buttons replaces the modal dialog.
