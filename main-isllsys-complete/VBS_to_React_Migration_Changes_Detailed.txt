  1. EXECUTIVE SUMMARY
================================================================================

The legacy Fulcrum / AQS Advantage application uses a single 9,090-line
VBScript file (Main_ISLLSYS_20010101.vbs) as its "shell controller" -- it runs
once when the application opens and provides ALL shared services to every content
page: navigation, command processing, security, focus management, dirty
tracking, and UI lifecycle.

The React migration (aqs-web-ui) has already rebuilt the framework: routing,
stores, schema-driven rendering, and server communication. What remains is
implementing the BEHAVIORAL logic that the VBScript file controlled -- the rules
that make the application actually work for underwriters.

This document covers 31 new React files to create + 8 existing files to modify
+ 1 startup configuration = 40 total files touched.

================================================================================
  2. THE BIG PICTURE -- HOW LEGACY EDITING WORKS
================================================================================

To understand WHY these changes are needed, you need to understand the legacy
editing loop. Every single data entry page in Fulcrum follows this exact cycle:

------------------------------------------------------------------------
STEP 1: Page Opens (window_onload)
------------------------------------------------------------------------

  What happens:
    The VBS captures every field's initial value as a "pristine baseline." It
    checks the action mode (ADD/EDIT/INQUIRY) and sets the dirty flag
    accordingly. If ShowNextOnEdit is configured, it disables or hides the Next
    button. It resolves security permissions to hide/disable controls the user
    shouldn't see. It builds the breadcrumb from the tree ancestry.

  React equivalent:
    pristine-store.ts captures baseline values. page-init-rules.ts handles the
    dirty flag and Next button. security-resolver.ts applies permissions.
    breadcrumb.tsx renders the path. use-page-init.ts orchestrates all of this
    per page load.

------------------------------------------------------------------------
STEP 2: User Edits Fields (the edit loop)
------------------------------------------------------------------------

  What happens:
    On every keystroke, the VBS checks: did a required field go from empty to
    non-empty (or vice versa)? If so, it re-evaluates whether OK/Next should be
    enabled. If ANY field value changes, it latches the dirty flag to true
    (one-way -- never goes back to false until save).

  React equivalent:
    use-edit-loop.ts watches form values via react-hook-form's useWatch. On
    empty<->non-empty flips, it calls runRequiredGate() from required-gate.ts.
    On any change, it sets dataChanged=true via GlobalVarsStore.

------------------------------------------------------------------------
STEP 3: User Tabs Out of a Field (focus exit)
------------------------------------------------------------------------

  What happens:
    This is the HEART of the legacy behavior. When the user tabs out of a field
    (blur/LostFocus), the VBS checks: did the value change from the pristine
    baseline? If yes AND the field has a "post-process action" configured in the
    schema, it makes a SERVER CALL. The server returns commands (SET_TEXT,
    SET_VALUE, NAVIGATE, DISPLAY_ERROR, etc.) that the VBS executes. This is how
    calculated fields update, validations run, and cascading changes happen --
    all triggered by tabbing out of a field.

  React equivalent:
    use-focus-roundtrip.ts provides onFieldBlur and onFieldFocus. On blur:
    compares current value vs pristine baseline, if dirty + has
    postProcessAction -> calls postEECall() via the ee-call.ts bridge -> runs
    returned commands via handlerForBrowserCommands. On focus: captures new
    baseline + runs pre-process if configured.

------------------------------------------------------------------------
STEP 4: User Tries to Leave (dirty guard)
------------------------------------------------------------------------

  What happens:
    If the user tries to navigate away or close the browser while dataChanged
    is true, the VBS intercepts with "You have unsaved changes. Are you sure?"
    If they confirm, it optionally sends a CANCEL beacon to the server to
    discard the pending transaction.

  React equivalent:
    use-dirty-guard.ts handles beforeunload + React Router useBlocker.
    use-unload-cancel.ts sends the CANCEL beacon via navigator.sendBeacon on
    pagehide.

------------------------------------------------------------------------

This 4-step cycle is the CORE of the application. Without it, the React app can
render pages but cannot actually DO data entry. Priority 1 delivers this cycle.


================================================================================
  3. PRIORITY 1 -- CORE EDIT LOOP (6 new files)
================================================================================

These 6 files deliver the complete editing cycle described above. Without these,
the React app can display pages but cannot do real data entry.
Estimated ~250-300 lines total.

------------------------------------------------------------------------
3.1  pristine-store.ts
------------------------------------------------------------------------

  React file:     src/stores/pristine-store.ts
  VBS routine:    #77 SetInitialValueData (line 8292)
                  + #55 SelectControlFocus (line 4903)
  Lines of code:  ~40

  What the Legacy VBS Does:
    When a page loads, SetInitialValueData loops through every control on the
    form and stores its current value in an array called mvntInitialValue. This
    is the "pristine snapshot" -- the original values before the user touches
    anything. Later, when the user tabs out of a field, SelectControlFocus
    compares the current value against this snapshot to determine if the field
    is "dirty" (changed). This is how the application knows whether to fire a
    server call on blur.

  What the React File Does:
    A Zustand store with four actions: captureAll(values) stores every field's
    value at page load. capture(matchcode, value) updates a single field's
    baseline on focus. isDirty(matchcode, currentValue) returns true if the
    field changed. clear() resets on page unload. The static-renderer and
    dynamic-renderer call captureAll after computing default values.

  Why It Matters:
    Without pristine tracking, the app cannot know which fields changed. The
    focus roundtrip (blur -> server call) would fire on EVERY blur, not just
    when a value actually changed. This would flood the server with unnecessary
    calls and break the editing experience.

------------------------------------------------------------------------
3.2  required-gate.ts
------------------------------------------------------------------------

  React file:     src/utils/required-gate.ts
  VBS routine:    #48 SetRequiredControl (line 4217)
                  + #49 CheckAllRequiredControls (line 4261)
  Lines of code:  ~45

  What the Legacy VBS Does:
    CheckAllRequiredControls loops through every control that has required=true
    in its schema definition. For each one, it checks: is the value empty? If
    ANY required field is empty, it sets the OK button and NEXT button to
    disabled. The moment ALL required fields have values, it enables them. This
    runs on every keystroke via ControlInputCheck.

  What the React File Does:
    Three functions: evaluateRequiredGate(fields, getValues) returns true/false.
    applyRequiredGate(fields, getValues) sets the disabled override on
    dtaOK/dtaNEXT via RuntimeOverrideStoreApi. runRequiredGate() combines both.
    Note: this only touches the "disabled" property -- never "visible" -- so it
    composes cleanly with ShowNextOnEdit rules that control visibility.

  Why It Matters:
    This prevents users from saving incomplete records. In the legacy app, if
    you leave a required field blank, the OK button stays greyed out. Users rely
    on this visual feedback. Without the required gate, users could submit
    incomplete forms.

------------------------------------------------------------------------
3.3  use-edit-loop.ts
------------------------------------------------------------------------

  React file:     src/hooks/use-edit-loop.ts
  VBS routine:    #71 ControlInputCheck (line 7197)
                  + #72 ControlInputChange (line 7267)
  Lines of code:  ~60

  What the Legacy VBS Does:
    ControlInputCheck fires on every keystroke (KeyUp event). It does two
    things: (1) If the field that changed is a required field AND it just went
    from empty to non-empty (or vice versa), it re-runs
    CheckAllRequiredControls to update the OK/Next button state. (2) It sets
    mblnDataChanged = True -- this is a one-way latch. Once any field changes,
    the dirty flag stays true until the page is saved or abandoned.

  What the React File Does:
    A React hook that uses react-hook-form's useWatch to subscribe to all field
    values. It maintains a map of "was this field empty last time I checked?"
    When a required field flips between empty and non-empty, it calls
    runRequiredGate(). When ANY field changes value, it sets dataChanged=true.
    Exports an <EditLoopBridge fields={mergedFields} /> component that you mount
    with one line inside the FormProvider.

  Why It Matters:
    This is the real-time responsiveness of the edit form. As the user types,
    buttons enable/disable, and the dirty flag latches. Without this, the form
    feels static -- users can't tell whether they've filled in enough fields to
    save.

------------------------------------------------------------------------
3.4  use-dirty-guard.ts
------------------------------------------------------------------------

  React file:     src/hooks/use-dirty-guard.ts
  VBS routine:    #38 window_onbeforeunload (line 2876)
  Lines of code:  ~30

  What the Legacy VBS Does:
    window_onbeforeunload is an IE event that fires when the user tries to
    close the browser or navigate away. The VBS checks: is mblnDataChanged
    true? Are there open child windows? If either is true, it shows "You have
    unsaved changes" and blocks navigation if the user clicks Cancel.

  What the React File Does:
    Combines two mechanisms: (1) beforeunload event listener for browser
    close/tab close, and (2) React Router's useBlocker() for in-app navigation.
    Both read dataChanged from GlobalVarsStore. Shows window.confirm() dialog.
    If the user confirms leaving, clears the dirty flag. Mount once in the root
    layout.

  Why It Matters:
    Data loss prevention. Without this, users can navigate away from a
    half-edited policy and lose all their work with no warning. This is a
    critical business requirement.

------------------------------------------------------------------------
3.5  use-focus-roundtrip.ts
------------------------------------------------------------------------

  React file:     src/hooks/use-focus-roundtrip.ts
  VBS routine:    #70 SelectControlFocus (line 7085)
                  + #74 SelectControlExit (line 7477)
  Lines of code:  ~70

  What the Legacy VBS Does:
    This is the HEART of the legacy editing system. SelectControlFocus fires
    when a user clicks into a field (GotFocus). It captures the field's current
    value as a new baseline. SelectControlExit fires when the user tabs/clicks
    out of a field (LostFocus). It compares the current value against the
    baseline. If different AND the field's schema declares a postProcessAction,
    it makes a server call (xmlServerCall). The server can return commands:
    SET_TEXT (update another field), SET_VALUE, DISPLAY_ERROR, NAVIGATE, etc.
    This is how calculated premiums update, address validation runs, and
    cascading field updates work.

  What the React File Does:
    A hook returning { onFieldFocus, onFieldBlur }. onFieldFocus(matchcode,
    value): captures pristine baseline via PristineStoreApi.capture(), runs
    pre-process binding if schema declares one. onFieldBlur(matchcode, value):
    checks isDirty vs baseline, if dirty AND field has postProcessAction ->
    calls postEECall() from the ee-call bridge -> runs returned commands via
    handlerForBrowserCommands. Wire onto field-renderer's input onFocus/onBlur
    events.

  Why It Matters:
    This is what makes "tab out of a field and something happens" work. Premium
    calculations, field validations, cascading updates -- all of these depend on
    the focus roundtrip. Without it, the application is a static form that
    cannot validate or calculate anything until the user hits Save.

------------------------------------------------------------------------
3.6  ee-call.ts
------------------------------------------------------------------------

  React file:     src/services/ee-call.ts
  VBS routine:    Infrastructure (xmlServerCall / handlerForEEData)
  Lines of code:  ~35

  What the Legacy VBS Does:
    In the legacy app, every server communication goes through two functions:
    handlerForEEData (builds the XML payload from the current form state) and
    xmlServerCall (posts it to the server and returns the response). These are
    deeply coupled to the VBScript runtime.

  What the React File Does:
    A configurable bridge with ZERO coupling to the client branch's internals.
    You call configureEECall({ post, buildPayload }) once at app startup,
    passing the repo's real xmlServerCall and handlerForEEData functions. After
    that, postEECall(args) and postRaw(payload) work everywhere. Until
    configured, they warn in the console and no-op -- the app still runs, just
    without server calls.

  Why It Matters:
    This is the zero-risk bridge pattern. All 31 new files that need server
    calls go through this bridge. If the client branch's server communication
    functions have different signatures than what we expected from the photos,
    you only need to change the configure call in ONE place, not in 15 different
    files.

4.1  security-resolver.ts
------------------------------------------------------------------------

  React file:     src/utils/security-resolver.ts
  VBS routine:    #45 SetControlAttributes (line 3830)
                  + #58-61 GetSecurity* (line 5250+)

  What VBS does:
    At page load, walks the permission tree for the current LOB/page. For each
    control, resolves visible/disabled/readonly from the permission node. Two
    modes: "allow" (missing node = fully allowed) and "deny" (missing =
    hidden+disabled).

  What React does:
    resolveControlSecurity() returns { visible, disabled, readOnly } per
    control. applySecurityPolicy() loops all fields and sets
    RuntimeOverrideStore. Handles both flat-array and nested-object permission
    shapes.

    NOTE: This is different from the team's SET_READONLY/SET_REQUIRED commands
    -- those are per-field from server responses; this is bulk permission
    resolution at page load.

================================================================================
  8. ONE-TIME STARTUP CONFIGURATION
================================================================================

In main.tsx (or root loader), configure the server communication bridge:

  configureEECall({ post: xmlServerCall, buildPayload: handlerForEEData });

Until configured, all server-dependent features warn in console and no-op --
the app runs either way. This means you can deploy the 31 new files
immediately. The server calls only activate when you wire the bridge.
