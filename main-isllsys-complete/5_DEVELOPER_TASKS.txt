TASK 6: Focus Roundtrip (blur -> server call -> run commands)
------------------------------------------------------------------------

  Depends on:  Task 5 (required gate + edit loop)
  Estimate:    5 hours
  Risk:        HIGH -- this is the HEART of the editing system.
               If it breaks, calculated fields, validations, and
               cascading updates stop working.

  WHY THIS MATTERS:
    When a user tabs out of a field and the value changed, the app makes a
    server call. The server returns commands (SET_TEXT, SET_VALUE, etc.)
    that update other fields. This is how premium calculations, address
    validation, and cascading updates work. This is THE most critical
    behavior in the entire application.

  FILES TO CREATE (1 new):
    1. src/hooks/use-focus-roundtrip.ts
       - Returns { onFieldFocus, onFieldBlur }
       - onFieldFocus(matchcode, value):
           * Captures pristine baseline via PristineStoreApi.capture()
           * Runs pre-process binding if schema declares one
           * Stamps mstrCurrentField in GlobalVarsStore
       - onFieldBlur(matchcode, value):
           * Checks isDirty vs pristine baseline
           * If dirty AND field has postProcessAction in schema:
             -> calls postEECall() from ee-call bridge
             -> runs returned commands via handlerForBrowserCommands
           * If not dirty: no server call (saves bandwidth)

  FILES TO MERGE INTO (1 existing):
    1. field-renderer.tsx
       - Wire onFieldFocus onto input's onFocus event
       - Wire onFieldBlur onto input's onBlur event
       - Pass matchcode and current value to each

  HOW TO TEST:
    - Open a page with a field that has postProcessAction in schema
    - Change the field value and tab out -> Network tab should show server
      call firing
    - Check that returned commands execute (e.g., another field updates)
    - Tab out WITHOUT changing value -> NO server call should fire
    - Tab out of a field WITHOUT postProcessAction -> NO server call
    - Open DevTools console -> no errors
    - Test with multiple field types: text, combo, date

  DONE WHEN:
    [ ] Tab out of changed field -> server call fires
    [ ] Tab out of unchanged field -> no server call
    [ ] Returned commands execute correctly
    [ ] Pre-process bindings fire on focus
    [ ] No regressions in existing field behavior
    [ ] THE EDIT LOOP IS COMPLETE (Task 1-6 together deliver full cycle)

TASK 8: Security Resolver
------------------------------------------------------------------------

  Depends on:  nothing (can start anytime)
  Estimate:    4 hours
  Risk:        MEDIUM -- affects which controls users can see/edit

  FILES TO CREATE (1 new):
    1. src/utils/security-resolver.ts
       - resolveControlSecurity(controlId, permissions, mode):
           returns { visible, disabled, readOnly }
       - applySecurityPolicy(fields, permissions):
           loops all fields, sets RuntimeOverrideStore
       - Handles "allow" mode (missing = allowed) and "deny" mode
         (missing = hidden+disabled)
       - Handles both flat-array AND nested-object permission shapes

  IMPORTANT NOTE:
    This is DIFFERENT from the team's SET_READONLY/SET_REQUIRED commands.
    Those are per-field commands from server responses (runtime).
    This is BULK permission resolution at PAGE LOAD (static).
    Both coexist -- they write to the same RuntimeOverrideStore but at
    different times and for different reasons.

  VERIFY AT INTEGRATION:

    - The photos showed two possible formats -- confirm which one the
      server actually returns
    - readNode path may differ per LOB

  HOW TO TEST:
    - Page with "allow" mode permissions -> controls without permission
      nodes should be fully visible/enabled
    - Page with "deny" mode permissions -> controls without permission
      nodes should be hidden+disabled
    - Permission with disabled=true -> control visible but greyed out
    - Permission with visible=false -> control completely hidden

  DONE WHEN:
    [ ] Security resolver correctly hides/disables controls
    [ ] Both permission modes work
    [ ] RuntimeOverrideStore values set correctly
    [ ] No conflicts with team's SET_READONLY/SET_REQUIRED
